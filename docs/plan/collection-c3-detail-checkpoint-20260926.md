# C3 详情提交与恢复检查点

基线：`587cd1f46`。详情执行、来源选择、证据保全和故障恢复已实现并通过聚焦验证。
C1-C3 中间里程碑的 fast 时间门禁尚未通过；本检查点不作为可部署候选。

## 已实现

- 用 `DetailStorage`、`DetailRuntime`、`DetailModels` 分别表达持久化、运行态和模型依赖。
  文件处理入口按实际 adapter 选择提取器，generic 不调用司法拍卖提取器。
- 付费提取前确认 seed 可读；日志和失败回执只包含 item、阶段和错误类型，
  不保存原始模型响应或异常中的敏感内容。遥测失败不控制提交结果。
- 明确执行顺序：读取输入、提取、来源校验、原始证据、侧文件、JSON、DB、运行态、清理。
  失败保留 HTML；相同输入的模型类失败两次后停止自动重试，存储失败按 30 秒退避。
  显式重试可继续处理，新 HTML 会清除旧失败与字段重试标记。
- 原始证据和侧文件按每次处理生成独立的 `capture-<revision>` 目录。
  已完成记录重新整理失败时，旧 DB 引用的证据保持原字节；后续成功也保留旧证据。
  既有归档路径仍可读取，没有数据迁移或自动清理。旧 TXT 输入和提取文本分别保存。
- HTML 发布和成功清理共用 dispatch lock；处理中到达的新输入不会被旧任务删除。
  AI 不能替换已确认的来源 ID、平台和 URL。来源字段不足时保留输入供下一次提取。
- 司法来源的证据字段规则迁到独立 profile，普通导出保留已知调用方。
  位置补充迁到独立职责模块，原服务 API 保留；其新 HTTP 入口在 C5 恢复。
- 包含 C2 类型整理引入的 Python 3.10 `typing.Self` 修复；类型专用导入放在
  `TYPE_CHECKING` 中，实际新进程已复测。

JSON、证据文件和 DB 没有跨文件事务。DB 失败时，候选 JSON 和独立证据可能已写入；
保留输入供检查与重试，不把这些写入描述成已回滚。
